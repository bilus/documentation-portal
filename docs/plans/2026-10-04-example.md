# Example: a portal application with bucket docs, previews and sign-in through Auth0 or GitHub

Issue: bilus/documentation-portal#37.
Ledger: `docs/plans/2026-10-04-example.ledger.md`.
Design: the example application's own leveled design, `examples/portalapp/docs/flow.dfd` (Q2); docportal's `docs/flow.dfd` and its child diagrams stay unchanged. Terms in `docs/vocabulary.md`; review page in `examples/portalapp/docs/review/index.html`, with the score card and the report beside it.
Branch: the worktree branch of this issue, at `origin/master` (`08d83a1`), which holds issues 34, 35, 26, 9, 36 and 8. Base: `08d83a1`.

## Requirements

Restated from issue 37's acceptance criteria, with requirements 10 and 11 from its description and technical notes.

1. The example application is a Go module of its own, `examples/portalapp`, whose dependencies stay out of the library's `go.mod`, and which builds against the library in the same checkout.
2. A sign-in page offers the configured identity providers, Auth0 and GitHub. The reader's choice starts the sign-in at that provider. A signed-in reader signs out from the navigation bar, which ends the session, and the reader's next request meets the sign-in page again.
3. An access file maps claims to the labels of the configuration file and to previews: Auth0's roles claim, or any other claim of the ID token, and a GitHub organization or team membership. A reader sees only the portals and sections without labels or with one of the reader's labels, in pages, links and the chat; the access file derives the reader's labels from the reader's claims.
4. The example serves the documentation of a bucket folder named by a Go CDK URL, refreshed every refresh interval as in #34, and opens previews as in #36. As the example rule, only the members of one GitHub organization open previews.
5. With an Anthropic API key in the environment, the example runs the chat, with one question limit for each signed-in reader, from any address.
6. With a `file://` bucket folder, a mock Auth0 (mockoidc) and a stub GitHub, the example starts with no cloud account and no Auth0 tenant, and a command of the example runs those mocks for a local run.
7. An end-to-end test signs two readers in through the mocks and checks that each sees only their own sections. A test builds the example and runs it against the mocks, in the steps of the README's local run.
8. The example's README lists the setup: the Auth0 application (callback and logout URLs, a post-login Action that adds namespaced claims), the GitHub OAuth app (callback URL, the `read:org` scope), the bucket with a read-only service account, the environment variables, the access file, the local run against the mocks, and the Dockerfile.
9. `make build`, `make lint`, `make test` and `make test-e2e` cover the example, so CI builds and tests it.
10. The example uses the library's documented API alone, and the root README documents every package of the API in the example.
11. GitHub signs readers in through the example's `signin.Provider`: GitHub's OAuth app endpoints, the reader from `GET /user`, and the memberships from `GET /user/orgs` and `GET /user/teams`, with the scope `read:org`.

Out of scope: a deployment, rules of docportal's own, a change to the library (the example tests the claim of #9, a program on the documented API alone, so a gap becomes a finding in the ledger), and a provider other than Auth0 and GitHub.

## Questions and assumptions

- Q1. The example's name and its module (the issue's first open question, and the brief's pointer). Assumption: `examples/portalapp`, the module `github.com/bilus/documentation-portal/examples/portalapp`, with `replace github.com/bilus/documentation-portal => ../..`. The replace directive keeps the root module untouched; a `go.work` at the root would put every `go` command of the repository into workspace mode, CI's included. A `go.work` in the example's directory would do no better than the directive, since the library must sit at a fixed relative path either way. The example's packages are `main` at the module's root, `mocks` and the command `cmd/mocks`.
- Q2. Where the example's design lives. Assumption: `examples/portalapp/docs/flow.dfd`, a top diagram of its own, with its own score card and review page beside it. A top diagram draws one program's startup, as `main.startup` reads like docportal's `docs/flow.dfd`, and the example's startup is another program's. dfdreview takes the directory above the design's directory as the code directory and type-checks the nearest module, so a design beside the example links its boxes to the example's code with types; one in the root's `docs/` would type-check the root module, which skips the nested module, and would key the example's `main` declarations against docportal's. docportal's diagrams need no change, since the example uses the library without changes. The vocabulary stays one file, `docs/vocabulary.md`, for both programs. In the example's design, the library is an outside package: a box names its functions by import path, as `github.com/bilus/documentation-portal/source.Load`.
- Q3. Two identity providers in one portal. Facts: `signin.Config` names one identity provider, and the sign-in middleware sends a reader without a session straight to it; both middlewares use the cookie names `signin_session` and `signin_attempt`, and each seals its cookies under a key derived from the session key and its own callback URL, so neither opens the other's cookie. Assumption: the example builds one sign-in middleware for each configured provider, around one previews handler, each with a callback path and a sign-out path of its own (`/auth/auth0/callback`, `/auth/auth0/sign-out`, `/auth/github/callback`, `/auth/github/sign-out`), and puts the sign-in router in front. The router answers `/sign-in`, the sign-in page, and `POST /sign-in/{provider}`, the choice, which sets the choice cookie and redirects to the return target; it sends a callback and a sign-out to the middleware of their path's provider, every other request to the middleware of the choice cookie's provider, and a reader without a choice to the sign-in page. Each middleware puts its provider's name into the request's context before the previews handler, so that the access hook knows the provider of the reader's sign-in.
- Q4. The choice cookie. Assumption: `signin_provider` (`__Host-signin_provider` with an https application URL), the provider's name, HttpOnly, SameSite=Lax, for `/` and 30 days, Secure over https. The choice is a POST from the sign-in page's form, under the check of `http.CrossOriginProtection`, so that no other site switches a reader's provider. A sign-out deletes the choice cookie, unless its Sec-Fetch-Site header says cross-site, when the middleware asks the reader first and keeps the session (README, Sign-in through an identity provider). The return target follows the rule of the sign-in package: a relative path on the portal's own origin, else `/`. A request without a choice that cannot follow a redirect, other than GET and HEAD or one that upgrades its connection, gets 403, as at the middleware's own start.
- Q5. The access file's format (the issue's first open question). Assumption: YAML, read once at startup from a local file, `PORTAL_ACCESS_FILE` (`access.yaml` by default), never from the bucket folder, so that whoever uploads documentation cannot grant themselves access. Under `labels:`, each label of the configuration file has a list of rules; under `previews:`, a list of previews rules. A rule has a provider name (`auth0` or `github`), a claim and values, and it matches a reader who signed in through that provider and whose claim, read with `signin.Claims.Strings`, holds one of the values. A GitHub rule names the claim `login`, `orgs` or `teams`, and its values match in any letter case, like GitHub's names; an Auth0 rule's match exactly. After defect finding 1, a GitHub rule may also name `id`, `org_ids` or `team_ids`, the numeric IDs, which never change hands, unlike names. The file refuses YAML errors, more than one document, unknown keys, a rule without a provider, claim or values, an empty value, an unknown provider and a GitHub claim of another name.
- Q6. The access hook. Assumption: `accessRules.access`, for `portal.Config.Access` and `portal.PreviewsConfig.Access`: it reads the provider's name from the request's context and the identity with `signin.IdentityOf`, and returns the reader's access, a `readerAccess`, whose zero value allows nothing: a portal or a section without labels opens to every signed-in reader, and one with labels to a reader with one of them, as in the README's example of Access per reader; the access is a `portal.PreviewAccess`, whose `Preview` opens every preview to a reader with a matching previews rule. A request without an identity or without a provider gets an access that allows nothing.
- Q7. The GitHub provider. Assumption: `githubProvider`, a `signin.Provider`: its endpoint is `github.Endpoint` of `golang.org/x/oauth2/github`, or with `GITHUB_URL` the same paths on that host, for the stub; its `Identity` reads `GET /user`, `GET /user/orgs` and `GET /user/teams` from `GITHUB_API_URL` (`https://api.github.com` by default) with the access token, following each list's `Link: rel="next"` pages, through an HTTP client of its own with a 30-second timeout, since the sign-in package documents no client in the context. The identity: the subject `github|` and GitHub's numeric user ID, in Auth0's form for a GitHub reader, so that a reader's subject never changes with the login; the name, else the login; the public email; and the claims `login`, `orgs` (organization logins) and `teams` (`org/team-slug`), in GitHub's spelling. An API error fails the sign-in. The scope is `read:org`. After defect findings 1 to 3: the claims also hold the IDs, `id`, `org_ids` and `team_ids`; the provider keeps only the organizations and teams named by a GitHub rule, by name or by ID, so that the session cookie's size follows the access file; and its client follows no redirect, so that the token reaches the API's host alone.
- Q8. Auth0. Assumption: through the OpenID Connect path, by its issuer. Auth0 adds custom claims to the ID token only under a namespace, through a post-login Action; the README's Action adds the reader's roles as `https://docs.example.com/roles`, and the demo's rules read that claim. RBAC permissions arrive in the access token's `permissions` claim, for an API, while the sign-in middleware takes the identity from the ID token alone: a rule on permissions needs the Action to copy them into the ID token, a step of the README. Rules read claims that the Action sets from `app_metadata` or the roles, never from `user_metadata`. The logout URL is a setting, `AUTH0_LOGOUT_URL`, since the example cannot tell Auth0's issuer from another's.

## The change in brief

The example application, a module of its own in `examples/portalapp`, is an embedding program built on the library's documented API. At startup it reads its settings from the environment and its access rules from the access file, opens the bucket folder of a Go CDK URL without its previews location, loads the published documentation's snapshot, and builds its portal handler with the access hook, the account hook of the sign-in and, with an API key, the chat with the reader hook of the sign-in; the reloader refreshes the snapshot, and the previews handler opens preview folders to the readers of the access file's previews rules. In front, a sign-in middleware for each configured identity provider, Auth0 by its issuer and GitHub through the GitHub provider, wraps the previews handler, and the sign-in router offers the providers on the sign-in page, keeps the reader's choice in the choice cookie, and sends each request to the middleware of the reader's provider. The access hook turns the reader's provider and claims into labels and a preview answer, so that each reader sees only their own sections. The mocks, a mock Auth0, a stub GitHub and a stub model, let the tests and a local run go without a cloud account.

## Metaphor

A museum whose room doors carry colored locks. The front desk checks a visitor's card from one of two issuers and fastens a wristband that copies the card's entries. The guard's list says which entries open which colors; a door without a lock opens to every wristband.
