## Requirements

Restated from issue 8's acceptance criteria, with requirements 12 and 13 from the working assumptions of Q7, Q11 and Q13.

1. With the sign-in middleware around the portal handler, opening any page without a session starts the sign-in at the configured identity provider, and a successful sign-in returns the reader to the page of the first request.
2. The return target travels in the sign-in attempt, sealed in a cookie and bound to its state, and must be a relative path on the portal's own origin: an absolute, protocol-relative or otherwise external target, a backslash or a control character falls back to `/`.
3. A successful sign-in issues a session with a new session ID.
4. A failed or cancelled sign-in shows the sign-in error page with a link to retry, and grants no access: no session cookie, and no request reaches the portal handler.
5. A signed-in reader can end the session at the sign-out path: the middleware deletes its cookie and revokes its session ID, so that a copy of the cookie stops working too.
6. Sessions expire after a configurable lifetime, 8 hours by default.
7. With an OpenID Connect provider, the sign-in checks `state`, uses PKCE with S256, and validates the ID token's signature, issuer, audience, expiry and nonce. A session cookie that is tampered with, expired, revoked, or sealed under another key, by another portal or for another cookie counts as none.
8. The embedding program reads the reader's identity (subject, name, email) and the provider's claims from the request's context through `signin.Identity` and `signin.IdentityOf`, types without a provider's name; `signin.AccountLinks` and `signin.ReaderID` are ready hooks for `portal.Config.Account` and `chat.Config.Reader`.
9. The sign-in settings and the sign-in configuration come from the deployment: docportal's flags and environment, or an embedding program's `signin.Config`, never the configuration file. docportal reads the client secret and the session key from the environment alone, and the client secret appears in no log line, no response and no URL of the browser.
10. The core packages import neither the sign-in package nor any OAuth or OpenID Connect library: `make lint`'s check refuses the sign-in package beside the libraries.
11. A provider without OpenID Connect, such as GitHub, plugs in through `signin.Provider`, which gives its endpoints and turns the access token into the reader's identity and claims; the sign-in checks the state and uses PKCE with it too.
12. docportal turns the sign-in on with an OpenID Connect provider through its flags; with an issuer, every page ends with the reader's name and a sign-out link, and the chat counts a signed-in reader's questions by the reader's subject. Sign-in settings without an issuer stop docportal at startup.
13. With the sign-in, every response to a signed-in reader is private, and the middleware's own responses carry `Cache-Control: no-store`.
14. Tests cover the sign-in, the callback, the sign-out, the return-target check and the token validation against `mockoidc` and a stub provider without OpenID Connect, with no real tenant, and a browser test signs a reader in through `mockoidc`.
15. The README documents the sign-in for an operator, with the configuration for Auth0, and for an embedding program.

Out of scope: the example application with GitHub (#37), docportal's own rules from claims (an embedding program maps claims to access with the access hook of #35), refresh tokens, an idle timeout, a revocation list shared by replicas, and the rotation of the session key.

## Questions and assumptions

- Q1. One module with the portal, or a module of its own (the issue's third open question)? Assumption: the package `signin` of this module, `github.com/bilus/documentation-portal/signin`, outside the core packages. docportal's flags need it, and a module of its own would need a replace directive for docportal and the browser tests, and a test run of its own. Go builds only the imported packages, so a program that imports `portal` alone links no OAuth library, and the module already requires `golang.org/x/oauth2` and `go-jose` through `gocloud.dev`, at the versions of `go-oidc` v3.21.0. `make lint` keeps the core packages from importing it. The tests add `github.com/oauth2-proxy/mockoidc`.
- Q2. The middleware's API. Assumption: `signin.New(ctx, signin.Config, next) (http.Handler, error)`, as `portal.New` returns the portal handler. It checks the configuration, and for an issuer discovers the provider's endpoints at once, so that docportal stops at startup on a wrong issuer. The middleware answers two routes of its own, the callback URL's path and the sign-out path (`Config.SignOutPath`, `/auth/sign-out` by default), and every other request needs a session. An embedding program mounts it at the root of the paths it guards, without `http.StripPrefix`.
- Q3. The sign-in session. Assumption: a sealed session cookie, which keeps the portal stateless, as the issue's technical note proposes. AES-256-GCM seals it under a key derived with HKDF-SHA-256 from `Config.Key`, 32 bytes or more, and from the callback URL, with the cookie's name as additional data, so that the browser can neither read nor change it, one portal's cookie opens in no other, and an attempt cookie never passes for a session. It holds a random session ID, the identity with the claims, and the expiry. It is `HttpOnly`, `SameSite=Lax` and for `/`, and with an https callback URL `Secure`, under the prefix `__Host-`. A session whose claims make the cookie longer than 4000 bytes fails the sign-in with the sign-in error page, so that no browser drops the cookie and loops.
- Q4. Must sessions be revocable on the server (the issue's fourth open question)? Assumption: sign-out revokes the session's ID in the middleware's memory until the session's expiry, and the middleware refuses a revoked ID, so that a copy of the cookie stops working in that process. The list holds only the sessions that ended early, each until its expiry. Another replica, or docportal after a restart with the same key, knows nothing of the revocation: the README says so, and a short lifetime bounds the exposure. A shared store waits for a need.
- Q5. Federated logout (the issue's first open question)? Assumption: the operator's choice, by the logout URL. Sign-out sends the reader to `Config.LogoutURL`, such as Auth0's `/v2/logout` with `client_id` and `returnTo`, which ends the provider's session too. Without one, the middleware's signed-out page links `/`, whose sign-in may pass at once while the provider's session lasts.
- Q6. Session lifetime, idle timeout and refresh tokens (the issue's second open question)? Assumption: a fixed lifetime from the sign-in, 8 hours by default, configurable; no idle timeout; no refresh tokens, since the portal reads the identity once, at the callback. A change of the reader's claims at the provider reaches the portal at the next sign-in, so the lifetime bounds the claims' age.
- Q7. Does docportal support a provider without OpenID Connect (the issue's fifth open question)? Assumption: the issue's working assumption: docportal's flags name an OpenID Connect provider alone, and GitHub needs an embedding program's `Provider`, as in #37.
- Q8. The sign-in attempt. Assumption: the attempt cookie keeps the state, the nonce, the PKCE verifier and the return target for ten minutes, sealed as the session cookie is, for the callback path alone. The callback refuses an attempt that is missing, expired or of another state, and deletes the cookie. A second sign-in in the same browser replaces the first one's attempt, whose callback then fails with the retry link. After finding 5 of the defect review, the attempt cookie is for / and, over https, named __Host-signin_attempt, so that no sibling host can plant one; after finding 4, an attempt whose cookie would pass 4000 bytes returns the reader to /.
- Q9. Requests that cannot follow a redirect. Assumption: a request without a session other than GET and HEAD, or one that upgrades its connection, such as the chat's socket, gets 403 without a redirect and without an attempt, since a browser can replay no body and follow no redirect in a socket's handshake.
- Q10. The identity. Assumption: from the ID token's claims: the subject from `sub`, the name from `name`, else `preferred_username`, the email from `email` as given, verified or not, and every claim of the token in `Claims`. A Provider gives the identity whole. An identity without a subject fails the sign-in. `IdentityOf` returns a deep copy, so that no hook's change reaches another hook.
- Q11. Private responses. Assumption: the middleware sends each signed-in reader's request through `portal.Private`, so that no shared cache gives a reader's page to another, even in a program that sets no hook; its own redirects and pages carry `Cache-Control: no-store`.
- Q12. The client secret. Assumption: docportal reads the client secret and the session key from `DOCPORTAL_OIDC_CLIENT_SECRET` and `DOCPORTAL_SESSION_KEY` alone, so that neither shows in the process list or in the usage's defaults. The middleware sends the secret to the token endpoint alone; its errors name settings, never the secret's value; and its log lines replace the secret, plain or query-escaped, with a marker, since a provider may repeat the secret in an error's body, as `mockoidc` does.
- Q13. docportal's hooks and flags. Assumption: with an issuer, docportal sets `portal.Config.Account` to `signin.AccountLinks` and, with a chat model, the chat's reader hook to `signin.ReaderID`; it sets no access hook, so every signed-in reader sees every portal. Without an issuer, docportal stays as it is today, byte for byte. The flags are `-oidc-issuer`, `-oidc-client-id`, `-oidc-callback-url`, `-oidc-logout-url`, `-oidc-scopes`, `-oidc-audience` and `-session-lifetime`, each with its `DOCPORTAL_` variable. A sign-in setting without an issuer stops docportal, which would otherwise serve every reader without a sign-in. Without a session key, docportal makes a random one and writes a line to the log.
- Q14. Timeouts. Assumption: the middleware's requests to the provider, the discovery, the keys, the token exchange and a Provider's requests through the context's client, use an HTTP client with a timeout of 30 seconds.
- Q15. The dependency check. Facts: the check of `make lint` runs `go list -deps` over the core packages and over docportal's imports apart from the GCS and S3 drivers, and docportal now imports `signin`, which imports `golang.org/x/oauth2` and `go-oidc`. Assumption: the check skips `signin` among docportal's imports, as it skips the drivers, and refuses `signin`'s import path in the core packages, beside the libraries. origin/master's check, from #41, covers the core packages alone; the rebase keeps that form and adds `signin` to the refused list.
- Q16. Design. `flow.dfd` gains three boxes: box 14, after box 11, makes the sign-in configuration of the sign-in settings, with a random session key and a notice in the log when the settings hold none (`main.signInConfigOf`); box 12, after box 14, wraps the previews handler in the sign-in middleware, with an issuer (`main.signIn`); and box 13, between boxes 5 and 6, adds `signin.AccountLinks` as the account hook (`main.addAccount`). Box 6 takes the issuer, for the chat's reader hook. The previews handler passes box 14 on its way to box 12. The new `flow.12.dfd` draws the steps of `main.signIn`, within package signin: box 12.1 builds the middleware (`signin.New`), with the discovery at `<Identity provider>` and a Provider's endpoint, and box 12.2, the middleware's answer to each request, follows `{HTTP server}`, as `flow.3.dfd` draws box 3.4. ## The change in brief

An embedding program, or docportal with an issuer, wraps the portal handler in the sign-in middleware of the package `signin`, which signs each reader in through an identity provider: an OpenID Connect provider by its issuer, with state, PKCE and a verified ID token, or a provider without OpenID Connect through a `Provider`. A reader without a session goes to the provider and comes back through the callback to the page of the first request, with a new session in a sealed cookie; a failed sign-in shows the sign-in error page with a retry link. The middleware puts the reader's identity and claims into each request's context for the request hooks: `signin.AccountLinks` gives the account hook the reader's name and a sign-out link, and `signin.ReaderID` gives the chat's reader hook the subject. Sign-out revokes the session until its expiry and sends the reader to the logout URL or the signed-out page. docportal reads the sign-in settings from its flags and its secrets from the environment, and `make lint` keeps the core packages free of the package and of every OAuth library.
