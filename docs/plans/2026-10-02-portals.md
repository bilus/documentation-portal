# Portals: named sets of sections, each under its own URLs

Issue: bilus/documentation-portal#3, re-scoped by the user on 2026-10-02.
Ledger: `docs/plans/2026-10-02-portals.ledger.md`.
Design: `docs/flow.dfd` and `docs/flow.3.dfd`, terms in `docs/vocabulary.md`, review page in `docs/review/index.html`.
Branch: `bilus/development`, which tracks `origin/master`. Base: `6e45e77`.

## Requirements

Restated from the user's decisions of 2026-10-02: the configuration lists portals, each a named set of sections; a menu on the navigation bar switches between them, and the chat follows the portal.

1. `portal.Config` takes the documentation root and the portals as Go structs: `portal.Portal`, with a name and its sections, in place of the sections of #29.
2. `portal.ReadConfig` reads the portals from the configuration file, under `portals:`, each with `name` and `sections`, and each section as in #29. It refuses a key it does not know.
3. A portal's slug is its name by the rule of section slugs. Every page of a portal has a URL under `/portals/{portal slug}/`: the viewer page `/portals/{p}/specs/{s}`, the raw spec `/portals/{p}/api/specs/{s}`, the document list `/portals/{p}/docs/{s}/`, a document page `/portals/{p}/docs/{s}/{path}`, a raw file `/portals/{p}/raw/{s}/{path}` and the chat page `/portals/{p}/chat`. `/portals/{p}/` opens the portal's first section. The Elements assets stay at `/assets/elements/`.
4. With one portal, `/` opens its first section. With two or more, `/` is the home page, which links each portal by its name, in the order of the configuration.
5. The navigation bar shows the sections of the page's portal and its chat page, and on its right a portal menu: the name of the page's portal, which opens a list of links to every portal. Choosing a portal opens its first section. With one portal there is no menu.
6. docportal stops at startup on no portals, a portal without a name or with an empty slug, two portals with one slug, and the section problems of #29 in any portal. Two portals may hold sections with one slug.
7. A relative link in a document, and a toc entry, resolve within the document's portal: a target that only another portal serves leads nowhere.
8. One chat serves every portal: the chat page of a portal answers from that portal's sections, its heading and the model's instructions name that portal's APIs, its navigation bar has the portal menu, and the hourly question limit counts a client's questions in every portal together.
9. The rules of #13, #19, #20, #22 and #29 hold in each portal.

Out of scope: automatic discovery of specs and URLs by file path, which the original issue asked for; a portal with a root of its own, which waits for the git source (#4); branches (#6).

## Questions and assumptions

- Q1. One configuration file and one documentation root, its directory, for every portal; each input and toc path is relative to it.
- Q2. A slug set in the configuration. Assumption: not now, as for sections in #29; a renamed portal changes its URLs.
- Q3. The menu. Assumption: a list of plain links, with no script, labelled with the page's portal name; each link opens a portal's first section, not the same page in the other portal. With one portal there is no menu, since there is nothing to switch to.
- Q4. The home page. Assumption: titled "Portals", with a link to each portal's first section, labelled with the portal's name. It has no navigation bar of sections, since it belongs to no portal.
- Q5. A URL under `/portals/` with a slug of no portal. Assumption: a 404 error page that names the slug and links the home page.
- Q6. The library and the chat. Assumption: `portal.NewLibraries(cfg)` returns one library per portal, in order, in place of `NewLibrary`; a library gives its portal's name (`Name`), slug (`Slug`), the URL of its first section (`URL`) and the URL of its chat page (`ChatURL`). `chat.Config` takes the libraries; the chat holds an agent for each, with the tools and the instructions of its portal, and registers one page for each at its `ChatURL`, in one live-templ app, whose socket path is fixed. `Chat.Ask` takes the slug of the portal whose chat page asks.
- Q7. Existing tests change in stages: at the plan gate in their setup only, a portal around the sections and `portals:` in configuration files; at stage 1 the URLs that they expect, under `/portals/{p}/`; at stage 3 the chat's setup, with libraries in place of one library.
- Q8. Design. In the top diagram, box 7 reads the portals from the configuration file. In `docs/flow.3.dfd`, box 3.1 checks the portals and opens their sections (`portal.openPortals`), and box 3.3 routes each request to a portal's page by the portal's slug and the section's slug.
- Q9. Metaphor: none, as for the earlier issues.
- Q10. Reviews: the defect review of AGENTS.md, once, before the pull request, with its prompt split into files under 25,000 tokens each.
- Q11. Delivery: one pull request for the whole issue after the last stage's approval, with `Closes #3` at creation.
- Q12. The original text of issue 3 asked for automatic discovery and URLs by file path; its description is rewritten to these requirements, with a note of what was dropped.

## The change in brief

The operator now lists portals in the configuration file, each a named set of sections. Every page of a portal lives under `/portals/{portal slug}/`, and a menu on the right of the navigation bar opens any other portal; with one portal, `/` opens it directly, and with several, `/` lists them. Links and toc entries stay within their portal. One chat serves all portals: each portal's chat page answers from that portal and names its APIs, while a client's question limit counts across portals.

## Stages

Each stage ends with `devbox run make build lint test test-e2e`, the hole census (`grep -rn "HOLE(" --include='*.go' .`), the score card, the review page and a halt for review.

The plan gate changes the configuration inline, with its tests: `portal.Portal` and `portal.Config.Portals` in place of `Config.Sections`, `portal.ReadConfig` reading `portals:`, and the sample configuration with one portal. It declares `portal.openPortals` as a hole whose mock opens the first portal's sections with `openSections`, and the router serves that portal at today's URLs, so every existing test stays green once its setup holds a portal. It also declares the holes of the later stages with their signatures.
