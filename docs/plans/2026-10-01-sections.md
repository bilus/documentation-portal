# Mount specs and documentation folders as navigation sections

Issue: bilus/documentation-portal#29.
Ledger: `docs/plans/2026-10-01-sections.ledger.md`.
Design: `docs/flow.dfd` and `docs/flow.3.dfd`, terms in `docs/vocabulary.md`, review page in `docs/review/index.html`.
Branch: `bilus/development`, which tracks `origin/master`. Base: `2dee6c1`.

## Requirements

Restated from the issue and the user's decisions: the library takes the documentation root as a filesystem and its configuration as Go structures, and it can read the configuration from YAML.

1. `portal.Config` takes the documentation root as an `fs.FS` and the sections as Go structs: a title, a type (`spec` or `docs`), an input path inside the root, and for a docs section an optional toc path inside the root.
2. `portal.ReadConfig` reads the sections from a YAML file of the root, under `sections:`, each with `title`, `type`, `input` and `toc`. It refuses a key it does not know.
3. docportal reads the configuration file that `-config` or `DOCPORTAL_CONFIG` names, `./environment.yaml` by default, and serves the directory that holds it as the documentation root through `os.Root`. `-root-dir`, `-spec-path`, `-docs-path` and `-toc-path` go, with their environment variables; `-addr`, `-hide-try-it` and `-chat-model` stay.
4. The navigation bar links each section in order, under its title, and the chat page when a chat model is named. `/` opens the first section's page.
5. A spec section has a viewer page at `/specs/{slug}`, which shows its raw spec from `/api/specs/{slug}`.
6. A docs section has a document list at `/docs/{slug}/`, a document page at `/docs/{slug}/{path}` for each markdown file, raw images at `/raw/{slug}/{path}`, and a sidebar laid out by its toc file, or else from its markdown files.
7. A section's slug is its title in lower case, with each run of characters other than letters and digits as one dash, and no dash at either end. docportal stops at startup on no sections, a section without a title, with an empty slug or without an input, an unknown type, two sections with one slug, an input or a toc path outside the documentation root, a docs input that names no directory reached through no symlink, and a toc on a spec section. A spec input with no file behind it is no error at startup: its viewer page answers 404, as today.
8. A relative link in a document, and a toc entry, open the page of the section that serves its target: the viewer page of the spec section whose input is the target, or the document page of the docs section whose folder holds it.
9. The chat's tools read every section: the guides of each docs section, and the operations and parts of each spec section.
10. The rules of #13, #19, #20 and #22 hold for each section: no symlink in a docs folder, nothing hidden, `x-doNotPublish`, link resolution, the toc's layout and its fallback.

Out of scope: a git-backed root (#4), a slug set in the configuration (Q2), and branch switching (#6).

## The change in brief

The operator now lists sections in a configuration file at the documentation root: specs and documentation folders, each under a title of the navigation bar. A spec section has a viewer page, and a docs section a document list, document pages, raw images and a sidebar, laid out by its own toc file when it names one. Each section's URLs carry a slug of its title, and a link or a toc entry opens the section that serves its target. Programs that mount the portal pass the same configuration as Go structs, with the documentation root as any filesystem; docportal's root is the directory of the configuration file. The chat reads every section.

## Stages

Each stage ends with `devbox run make build lint test test-e2e`, the hole census (`grep -rn "HOLE(" --include='*.go' .`), the score card, the review page and a halt for review.

The plan gate changes the configuration inline, with its tests: `portal.Config.Sections` with `portal.Section` in place of `SpecPath`, `DocsPath` and `TocPath`; `portal.ReadConfig`; main's `-config` and `DOCPORTAL_CONFIG`, `main.openRoot` of the configuration file's directory and the call of `portal.ReadConfig`, in place of the four flags; and `testdata/environment.yaml`, the sample configuration. It declares `portal.openSections` as a hole whose mock checks and opens the first spec section and the first docs section as `portal.checkConfig` did, and `portal.newSite` gives the site the first spec section's input and the first docs section's content directory, so the router serves them at today's URLs and every existing test stays green once its setup moves to sections. The other holes are declared with their stages' signatures and are not called yet: `slugOf`, `site.specFor`, `site.docsFor`, `Library.Sections` and `Library.SpecPart`, whose mock reads the first spec section.
