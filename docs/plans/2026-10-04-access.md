# Access per reader: portals and sections restricted by an access hook

Issue: bilus/documentation-portal#35.
Ledger: `docs/plans/2026-10-04-access.ledger.md`.
Design: `docs/flow.dfd`, `docs/flow.3.dfd`, `docs/flow.3.4.dfd` and `docs/flow.9.dfd`; terms in `docs/vocabulary.md`; review page in `docs/review/index.html`.
Branch: `bilus/development`, which tracks `origin/master`. Base: `b6ac5fd`.

## Requirements

Restated from issue 35's acceptance criteria, with requirement 11 from the working assumption of its first open question.

1. Without an access hook, every reader sees every portal and section, and the responses stay as they are today, without Cache-Control.
2. The home page and the portal menu list only the portals visible to the reader. With one visible portal, `/` opens it. With none, the home page says so.
3. The navigation bar lists only the sections visible to the reader, and `/portals/{p}/` opens the first of them.
4. Every route of a portal or a section hidden from the reader (viewer page, raw spec, document list, document page, raw file, chat page) answers with the same 404 page as a missing portal or section.
5. A toc entry or a markdown link to a page of a section hidden from the reader counts as a link to a missing page: the sidebar leaves out the entry, and the markdown link shows as plain text.
6. The chat of a visible portal answers only from the sections visible to the reader: its search, document and operation lookups skip the hidden sections, and the chat model's instructions name only the visible APIs. The chat page's heading, navigation bar and portal menu show only the visible APIs, sections and portals.
7. An error from the hook hides everything from the reader, and goes to the log.
8. With a hook, every response carries `Cache-Control: private`.
9. Tests use a stub hook, which reads the visible sections from a request header.
10. The README shows an embedding program: a middleware that puts claims into the request's context, and a hook that maps them to portals and sections.
11. A portal and a section of the configuration file take an optional list of labels. `portal.ReadConfig` reads them, and the hook receives them with the rest of the portal or the section.

Out of scope: rules by roles and permissions (#10), the extension API (#9), and a question limit per reader of the embedding program (#26).

## Questions and assumptions

- Q1. The hook. Assumption: the issue's shape, `portal.Config.Access func(r *http.Request) (portal.Access, error)`, with `type Access interface { Portal(p Portal) bool; Section(p Portal, s Section) bool }`. The portal handler calls the hook once for each request, and its result answers every check of that request. Without a hook, the handler calls nothing and adds no header, and `portal.Everything`, an access that allows every portal and section, stands for every reader.
- Q2. What identifies a portal or a section to the program's rules. Assumption: the hook receives the `Portal` and the `Section` of the portal configuration as given, before the portal cleans the paths, so that a rule can compare them with its own copy of the configuration; both gain an optional `labels` list, such as `labels: [partner-acme]`. The portal handler does not use the labels. A label survives the rename of a section, unlike its slug, so the README's example rules name labels.
- Q3. Visible. Assumption: a section is visible to a reader when the reader's access allows its portal and the section; a portal is visible when the access allows it and at least one of its sections. A portal allowed without any section counts as hidden, so that no reader gets a portal with an empty navigation bar.
- Q4. A hidden portal or section answers as a missing one. Assumption: for each request, the router builds the reader's view, the reader's access with the reader's sites, a copy of each visible portal's site with only its visible sections, and every page, link, toc entry and library lookup of the request reads those copies through the code that already answers a missing portal or section. The chat page of each portal, a route of the chat, answers through the same check as the other routes of its portal.
- Q5. A reader with no visible portal. Assumption: the home page, with status 200 and the message "No portals are open to you.", as the acceptance criteria say; a 403 page for the program to style waits for a need.
- Q6. A failed hook. Assumption: an error hides everything from the reader and writes `access hook: <error>` to the log, once for each request; a nil access with a nil error counts as an error too. The README asks the program to return an access that hides everything for a reader without rights, and an error only for a failure, such as a permission service out of reach.
- Q7. `Cache-Control: private`. Assumption: the portal handler wraps the response writer of each request with a hook, and the wrapper sets the header as the status goes out, so that a response whose handler deleted the header first, as Go's file server does on an error (`net/http/fs.go`, `serveError`), carries it too. The wrapper hands over the connection for the chat's socket (`Hijack`) and unwraps for `http.ResponseController`.
- Q8. An open chat page and a change of the reader's access. Assumption: the change reaches an open chat page at its next load. live-templ mounts a page again at the join with a context of its own and the page session, signed at the page's GET, and without a request (`interpreter.New`, `Interpreter.join`), so the chat cannot call the hook at the join or at a question. The page's GET passes through the portal handler, which calls the hook; the chat's session reader turns the reader's access into the titles of the visible sections of each portal, by the name of the portal, and live-templ signs them into the page session. The page's mount and each of its questions read that access. A reader cannot widen it, since live-templ signs the page session. Without a hook, the page access allows everything, so an open page answers from each new snapshot's sections; with one, it names each portal by a digest of its configuration, so that a later snapshot that changes a portal hides that portal from the open page until the page loads again, and one that changes nothing in it leaves the page as it was. A token of the page session joins for two weeks at most, and not after a restart, whose live-templ app signs with a new secret; a page already joined keeps its socket. This is the issue's first option, with the page's GET in place of the socket's upgrade request.
- Q9. The chat's lookups. Assumption: `Chat.Ask` takes the reader's access after the portal's slug, limits the portal's library with `Library.For(access)`, and answers a portal hidden from the reader with `ErrNoPortal`, as a missing one. The tools and the chat model's instructions read the limited library from the run's context, as the lookup budget does, so that one agent per portal still serves every reader. `portal.AccessOf(r)` gives the chat the access that the portal handler found for a request: the hook's access, or `Everything` without a hook. A request served by no portal handler gets an access that allows nothing, so that the chat's routes, mounted anywhere but in the Chat of the portal configuration, show nothing; the chat's tests reach their routes through a portal handler.
- Q10. Design. `flow.3.dfd` gains box 3.4, the portal handler's answer to each request (`router.ServeHTTP`), as `flow.9.dfd` draws box 9.4: an exception to the rule that a process's diagram holds the steps its function calls, since `portal.New` does not call it and box 9 sends it each request. The router travels to box 9 as the portal handler and comes back as the receiver of box 3.4, so no store holds it, as no store holds the reloader's source and builder. The new child diagram `flow.3.4.dfd` draws the answer's steps: 3.4.1 asks the access hook (`router.readerAccess`), 3.4.2 builds the reader's view (`router.viewFor`), asking the access about each portal and section, and 3.4.3 sends the request with the view through the routes (`router.route`), whose pages read the documentation root. The embedding program, the log, the documentation root and the HTTP server are external systems beside them. `ServeHTTP` is the diagram in code. Box 3 of the top diagram names the handler's answer. The chat's per-reader steps, the page session's round trip through the browser and the library in the run's context stay undrawn, as the chat's runtime has stayed since #25: they belong to a diagram of the chat's runtime, a change of its own. The top diagram stays as it is, since docportal sets no hook.
- Q11. Metaphor: none, as for the earlier issues.
- Q12. Reviews: the design review and the vocabulary review of the skill at the plan gate, by sub-agents, as the user asked on 2026-10-04 ("use design review by a sub-agent from time to time"); the defect review of AGENTS.md once, after the last stage.
- Q13. Delivery: one commit per filled hole, no pull request and no push; the main session reshapes the history and opens the pull request. The user lifted the halts of law 5 ("no need to ask for approval"), so each boundary records its handoff in the ledger and the work continues.
- Q14. The stub hook. Assumption: the package `internal/fakeaccess` serves the tests of `portal`, `chat` and `e2e`: its `Hook` reads the header `Sections`, a list of `portal name/section title` pairs separated by commas, such as `Pet Shop/API, Store/API`, and a request without the header sees nothing.
- Q15. A directory of two docs sections. Assumption: a visible docs section serves its whole content directory, so a file in the directories of a hidden section and of a visible section stays visible through the visible section, and links to it open there. The README says to keep a hidden section's directory out of every visible section's content directory.
- Q16. The router keeps one copy of each configured section: on the site, the configured portal with its sections, and on each section, its configured value, so that the access's check of a section does not depend on the order of two lists. Both copies are set once, in `openPortals`, and never change.
- Q17. A toc file's problem in the log. Assumption: the log judges a toc file by the whole portal, as before this change, so that no reader's access puts a line in the log or takes one out. A toc file whose pages are all hidden from a reader is no problem of the file: that reader's sidebar falls back to the markdown files, as for any toc that names no page, and the log stays as it is. A reader's site keeps the whole site for that check.

## The change in brief

An embedding program gives the portal configuration an access hook, which returns the access of each request's reader, such as from the claims of the program's own middleware. The portal handler calls the hook once for each request and sends the request with the reader's view through its routes, so that the home page, the portal menu, the navigation bar, every route, the links and the toc entries show only the visible portals and sections, and a hidden one answers as a missing one. With a hook, every response is private, and an error from the hook hides everything. The chat page keeps the access of its load in its signed session, and each of its questions reads the library that `Library.For` limits to that access. Labels on the portals and sections of the configuration file give the program's rules names that survive a rename.
