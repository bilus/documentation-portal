# Previews: a preview folder of the bucket folder, chosen by a cookie

Issue: bilus/documentation-portal#36.
Ledger: `docs/plans/2026-10-04-previews.ledger.md`.
Design: `docs/flow.dfd`, `docs/flow.3.dfd`, `docs/flow.3.4.dfd`, `docs/flow.9.dfd` and the new `docs/flow.11.dfd`; terms in `docs/vocabulary.md`; review page in `docs/review/index.html`.
Branch: a worktree branch, rebased onto `origin/master` before the pull request. Base: `0648a9d`, the tip of `bilus/development`, with issues 34, 35, 26 and 9.

## Requirements

Restated from issue 36's acceptance criteria, with requirement 9 from the working assumption of its second open question and requirement 10 from the brief of the work.

1. Previews are off unless the operator names a previews location, a folder of the bucket folder such as `previews/`, with `-previews` or `DOCPORTAL_PREVIEWS`. The published documentation's listing leaves the previews location out.
2. `/previews/{folder}` switches the reader to the preview folder of that name under the previews location and opens `/`. `/previews/{folder}/{path...}` opens `/{path...}` instead, so that a CI job can link a changed page.
3. In a preview, every page, raw file, raw spec and Elements request comes from the folder's snapshot (the Elements assets come with docportal, through the folder's portal handler), and every page shows a banner with the folder's name and a link out of the preview: `/previews/`, which takes the reader back to the published documentation at `/`.
4. A folder name is one path segment of letters, digits, `.`, `_` and `-`, other than `.` and `..`. Any other name, or a folder without a configuration file, gets a 404 page with the folder's name, and the reader stays in the preview or the published documentation of the request.
5. The portal loads a folder's snapshot at the folder's first request and refreshes it as #34 does. It drops a snapshot after an idle time, `-preview-idle` (`DOCPORTAL_PREVIEW_IDLE`), one hour by default, and keeps at most `-max-previews` (`DOCPORTAL_MAX_PREVIEWS`) snapshots in memory, 10 by default.
6. A deleted folder stops serving at the next check, and its readers return to the published documentation with a message.
7. With the access hook (#35), the application decides who may open previews. Without it, any reader may.
8. Responses in a preview carry `Cache-Control: private`.
9. A preview has no chat, and its navigation bar has no chat link.
10. The README documents previews for an operator and for a program that embeds the library, and a browser test opens a preview, sees the folder's document and the banner, and leaves the preview.

Out of scope: a URL prefix for each preview (Q1), a chat in a preview (Q2), previews of a local directory, and the CI job that uploads the folders.

## Questions and assumptions

- Q1. Cookie or URL prefix (the issue's first open question). Assumption: the preview cookie, `portal-preview`, holds the folder name of the reader's preview. The portal's URLs stay as they are, and the previews handler, in front of the published portal handler, sends each request to the portal handler of the cookie's folder. A URL prefix would need a base path for every URL of the portal and a socket path option in live-templ, whose chat socket has the fixed path `/live/websocket`: two changes beyond this issue, one of them in another module. The cost: one preview at a time in a browser, and page URLs without the preview's name; the link `/previews/{folder}/{path...}` carries both.
- Q2. A chat in a preview (the issue's second open question). Assumption: none. The preview builder builds a folder's portal handler as the builder does, without the chat, so the navigation bar has no chat link and a chat URL answers as a missing page. The chat, its libraries and its question counts belong to the published documentation, whose snapshots share one chat (#34), and a chat for each preview would spend model calls on unpublished documents.
- Q3. Defaults (the issue's third open question): an idle time of one hour and 10 snapshots, the issue's proposal. Each preview's snapshot holds up to the size limit, so the snapshots of docportal take up to eleven times the size limit, a warning of the README. Zero means none, as for the size limit and the refresh interval: an idle time of 0 drops no snapshot for its idleness, and a preview limit of 0 keeps any number; docportal refuses a negative value.
- Q4. The previews location. Assumption: a folder of the bucket folder, by its path inside it, such as `previews`, with an optional trailing slash. The published documentation's listing leaves out every key under it, so that no preview reaches a published page or counts against the published size limit. Each preview folder under it is a bucket folder of its own, with the same size limit and the same configuration file path. `-previews` needs `-root`. A folder of the bucket folder, rather than of the bucket, needs no second URL and works for a bucket folder at the bucket's root too. `source.Bucket` reads a folder through a key prefix of its own (`Bucket.Folder`) and leaves a folder out (`Bucket.Without`), so that the preview folders of the location share one open `*blob.Bucket`: `blob.PrefixedBucket` closes the bucket it wraps (Go CDK v0.46.0, `blob/blob.go:1631`), so it cannot give two folders of one open bucket. docportal opens the bucket twice, at box 2 for the published documentation and at box 10 for the previews location, so that neither box carries the bucket to the other.
- Q5. The snapshots. Assumption: `source.Previews` keeps them. `NewPreviews` takes a function that opens a folder by its name as a documentation source: in docportal, `Bucket.Folder` of the previews location, and in the tests, fake sources. At a folder's first request, `Previews.Handler` reads the folder's snapshot with `Load`, builds its portal handler with the preview builder, and wraps the handler in a reloader with the refresh interval, so that the folder refreshes like the bucket folder. Each request marks the folder's last use; a timer drops a snapshot unused for the idle time, and a load beyond the preview limit drops the least recently used snapshot, while a failed load drops none. Two first requests of one folder share one load. A dropped snapshot's checks stop, and the folder's next request loads it again.
- Q6. A deleted folder. Assumption: a check that lists no object in the folder drops its snapshot at once, so the reader's next request finds no folder. A folder that loses only its configuration file keeps its last snapshot, as #34 keeps a snapshot after a failed refresh, and the log gives the cause: a deletion of many objects removes one object at a time, and the check that counts is the one with an empty folder.
- Q7. The return with a message. Assumption: when the cookie's folder no longer opens for the reader (deleted, hidden from the reader, or a failed load), the previews handler clears the cookie and answers the same request from the published documentation, with a notice in the banner's place: "The preview pr-123 is no longer available." The notice cookie, `portal-preview-ended`, carries the notice past a response that is no page, such as a redirect or a raw file, and the first page with the notice clears the cookie. The cause of a failed load goes to the log.
- Q8. A name that does not open. Assumption: the previews handler passes a `/previews/{folder}` request whose folder does not open (an invalid name, a folder hidden from the reader, no folder, no configuration file, a failed load) to the published portal handler, with the reader's cookie unchanged and with the banner of the reader's preview, if any. The portal handler answers `/previews/{folder}` and `/previews/{folder}/{path...}` with the 404 page "Preview not found", which names the folder. Both read the name as ServeMux does, from one escaped segment, so `/previews/a%2Fb` names `a/b` and `/previews/%2e%2e` names `..`. A request with a bare `..` segment never gets that far: browsers resolve dot segments before they send a URL, and ServeMux redirects such a path to its clean form.
- Q9. Who may open previews. Assumption: `portal.PreviewAccess`, an `Access` with the method `Preview(folder string) bool`. With an access hook, a reader may open a preview only when the reader's access implements `PreviewAccess` and allows the folder; an access without the method opens no preview, so a program's existing hook opens none until the program adds the method. `Everything`, every reader's access without a hook, allows every preview. The previews handler asks the access hook once for each request with a folder to open, and the preview's portal handler asks its own hooks, as for any request. A preview cookie of a folder hidden from the reader ends the preview, which returns the reader to the published documentation with the notice (Q7).
- Q10. Privacy. Assumption: the previews handler marks private every response with a preview in it: a preview's responses, through the private handler of #35; the redirects at `/previews/`; the 404 page of a `/previews/` path; and every response with a notice. The published documentation's responses to a request without a preview stay unchanged.
- Q11. The cookies. Assumption: `portal-preview` and `portal-preview-ended` are session cookies with the path `/`, `HttpOnly` and `SameSite=Lax`, so that a link from another site, such as a pull request's page, switches the reader at its top-level navigation. A cookie value other than a valid folder name counts as none.
- Q12. Where the parts live. Assumption: the previews handler is in the package `portal`, as `portal.WithPreviews(published, portal.PreviewsConfig{Open, Access})`, so that the banner, the private handler and the page templates stay in one package; in docportal, `source.Previews.Handler` is `Open`. An embedding program wires the two like docportal. Without `Open`, `WithPreviews` returns the published portal handler itself.
- Q13. Design. The top diagram gains box 10, which opens the previews location into the previews configuration (`main.openPreviews`) with the preview builder, and box 11, which wraps the reloader in the previews handler (`portal.WithPreviews`, with `previews.ServeHTTP`, the diagram in code of its child diagram); box 2 leaves the previews location out of the bucket folder's listing. The new child diagram `flow.11.dfd` draws the previews handler's answer to each request, like box 9.4 in `flow.9.dfd`: 11.1 reads what the request asks of the previews (`portal.readPreviewRequest`), 11.2 asks the access hook (`previews.readerAccess`), 11.3 opens the folder's portal handler (`previews.openFolder`), and 11.4 answers (`previews.send`); `previews.ServeHTTP` is the diagram in code. Box 11.3 draws the preview snapshots as a store, read and written through Open, and the preview access's answer as an exchange with the embedding program. Each preview folder in memory has a reloader of its own, process 9, whose checks drop the snapshot at a listing without objects; that drop, the idle timer and the preview limit run inside `source.Previews`, behind Open, and the header of `flow.11.dfd` describes them, as `flow.3.4.dfd` draws the chat's state behind box 3.4.3 and leaves the chat's runtime undrawn. Box 3.3 names the 404 page of a preview, and the header of `flow.3.4.dfd` says that the banner rides in the request's context to the pages of box 3.4.3.
- Q14. Metaphor: none, as for the earlier issues.
- Q15. Reviews: the design review and the vocabulary review of the skill at the plan gate, by sub-agents (Opus for the design review, Sonnet for the vocabulary review), as the user asked ("observe the metrics and use design review by a sub-agent from time to time"); the defect review of AGENTS.md once, after the last stage.
- Q16. Delivery: one commit per filled hole, no pull request and no push; the main session reshapes the history and opens the pull request. The user lifted the halts of law 5 ("no need to ask for approval"), so each boundary records its handoff in the ledger and the work continues. ## The change in brief

The operator names a previews location inside the bucket folder with `-previews`, and a CI job uploads each pull request's documentation to a preview folder under it. docportal leaves the previews location out of the published documentation and wraps the reloader in the previews handler. A link to `/previews/{folder}` switches the reader to that preview: the previews handler checks the folder name and the reader's access, opens the folder's portal handler, sets the preview cookie and redirects. From then on it sends each request of that reader to the preview's portal handler, privately, and every page shows the banner, until the reader leaves at `/previews/`, or until a request finds the folder closed to the reader or gone, which returns the reader to the published documentation with a notice. `source.Previews` loads a folder's snapshot at its first request, refreshes it with a reloader of its own, and drops it when idle, beyond the maximum, or when a check finds the folder deleted. A preview has no chat.
